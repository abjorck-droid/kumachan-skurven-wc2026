   25, halves to **12** not 13) and the All-In ordering (1000×5×0.5 = 2500).

2. **Entry server** (`scripts/pickentry_server.py`):
   - `mulligan_guard()` — pure, raise-before-write (mirrors `bracket_guard`): window, one-per-player
     budget, target ownership/eligible type, no-op, **Dark-Horse eligibility (rank > 16)**, token
     budget, and for a bracket-slot swap it **re-runs `bracket_guard`** on the post-swap set.
   - `save_mulligan(..., dry_run=False)` — writes the replacement as a **sibling row**
     (`<player>|<key>|mull`) so the original survives and the engine halves **both**; logs an
     idempotent `Mulligans` link; spends the mulligan **last** (safe-retry order). `dry_run=True`
     validates and returns the planned writes under `wouldWrite`, committing nothing.
   - New `POST /api/mulligan` (`{player,target,replacement,note,dryRun}`); bootstrap now returns
     `mulligansRemaining`. Constants: `MULLIGAN_WINDOW=("2026-06-26","2026-06-28")`,
     `DARK_HORSE_MAX_RANK=16`. Tests: `tests/test_mulligan_entry.py` (26).

## How the tab gates (so the next session doesn't get confused)

The Mulligan tab is gated on **being locked, not on the window**. Both players are locked, so the tab
shows **now** — it'll appear as a new tab on the updated page. The June 26–28 **window** only gates
the *actions*: before the 26th the panel renders with an "opens June 26, preview-only" notice and the
server rejects Preview/commit; once the window opens the same buttons go live. No new tab appears at
window-open — it's already there by virtue of the lock.
